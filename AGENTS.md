# AGENTS.md

Guidance for working in this repository. Read this before making changes.

zuke-python is the Python SDK for [Zuke](https://github.com/zuke-build/zuke),
the code-first, strongly-typed build automation system. A Zuke build written in
Python is a class whose fields are targets; this package hosts that class as a
**worker** and runs it on the Zuke **engine**, which stays in the main
repository.

> This file, `AGENTS.md`, is the single source of truth for both humans and
> agents. `CLAUDE.md` is a thin pointer whose entire content is `@AGENTS.md`, so
> Claude Code loads this file and there is exactly one copy to maintain.

## Status and sequencing

The SDK was gated on the engine. The order of work, decided in the main
repository, is:

1. The engine becomes fully separate: it can host a build another process
   describes over the worker protocol, and a conformance suite proves it against
   a fake worker. Done, in the main repository:
   [phase 0](https://github.com/zuke-build/zuke/issues/901) and
   [phase 1](https://github.com/zuke-build/zuke/issues/903); `@zuke/engine`
   1.0.0 speaks protocol v1.
2. Then this package gets the authoring surface, the worker loop, and the
   generated tool facades, and its own build becomes a Zuke build. Done, slice
   by slice, under [#3](https://github.com/zuke-build/zuke-python/issues/3);
   the package is published on PyPI as `zuke` from 1.0.0.

The worker loop (`_rpc.py`, `_worker.py`), the authoring surface (`_dsl.py`,
`_build.py`, `_ci.py`, `_settings.py`, `_run.py`), the body and service
contexts (`_context.py`), the hooks and the conformance replay are in, and this
repository's own gate is a Zuke build (`build.py`) run by `@zuke/engine` at the
version `zuke.json` pins. The tool facades under `src/zuke/tools/` are
generated by `_generate.py` from the engine's tool spec, vendored under
`spec/` at the tag `spec/engine.json` names, over the runtime in `_facade.py`;
`facades_check` in the gate fails when they drift from the spec.

## How the SDK relates to the engine

- **One engine, thin SDKs.** The engine owns scheduling, retries, timeouts,
  cancellation, durable run records, resume, locks, caching, services, CI
  generation, the MCP server, the registry, rendering, redaction, and every tool
  wrapper. The SDK owns the authoring surface (`Build`, `target()`,
  `parameter()`, `group()`, `service()`), the manifest it describes, and running
  a target body when asked.
- **Every subprocess runs in the engine.** A body calls `ctx.sh(...)`, which is
  an `exec` request over the socket; the engine spawns it with argv purity,
  tee and capture, redaction, dry-run, timeout kill and cancel. The worker sends
  its own environment and working directory in `hello`, and the engine uses
  them as the base of every spawn, so a `uv run` venv PATH is honoured.
- **Transport:** newline-delimited JSON-RPC 2.0 over loopback TCP. The engine
  listens, hands the worker `ZUKE_ENGINE_ADDR`, `ZUKE_ENGINE_TOKEN` and
  `ZUKE_PROTOCOL`, and accepts exactly one connection. The worker's stdout and
  stderr go to the engine as log lines, so a stray `print` cannot corrupt the
  protocol. The worker ignores SIGINT; the engine drives shutdown.
- **The protocol is defined in the engine repository**, with its conformance
  transcripts. This repository pins the engine release it was tested against. A
  protocol change lands in the engine first; the SDK change that uses it pins
  the engine version that carries it.
- **Tool facades are generated**, by `src/zuke/_generate.py` from the engine's
  tool spec (`packages/engine/spec/tools.json` there, vendored here under
  `spec/` by `./zuke vendor_spec`), never hand-written. A new wrapper, or a
  change to one, belongs in the engine repository; `./zuke facades` regenerates
  `src/zuke/tools/` after `vendor_spec` brings the new spec, and `./zuke
  facades_check` is in the gate.

## Tech stack

- **Runtime:** Python 3.12+. The package has **no runtime dependencies**;
  everything it needs is in the standard library (`socket`, `json`, `asyncio`,
  `contextvars`). The development tools are in the `dev` dependency group.
- **Toolchain:** [uv](https://docs.astral.sh/uv/) for environments and the
  lock, [ruff](https://docs.astral.sh/ruff/) for formatting and linting,
  [pyright](https://github.com/microsoft/pyright) in strict mode for types,
  [pytest](https://docs.pytest.org/) with coverage and pytest-asyncio. The
  gate's targets are `build.py`, a Zuke build the engine runs through the
  `./zuke` launchers, which bootstrap Deno themselves.
- **Distribution:** `zuke` on PyPI, versioned by release-please from the
  squash-merged PR titles, as in the main repository. The `release` workflow,
  generated from `build.py`'s `release_workflow` field, runs on every push to
  `main`: release-please maintains the release PR from
  `.release-please-config.json` and `.release-please-manifest.json`, bumping
  `__version__` in `src/zuke/__init__.py`, the one place the version lives:
  `pyproject.toml` declares it dynamic and hatchling reads it from there, so
  `uv.lock` records no version and a release PR passes `uv sync --locked`
  untouched. When a release is cut the `publish` target builds the sdist and
  the wheel with uv, signs each one's PEP 740 provenance attestation with
  PyPA's `pypi-attestations` from the job's OIDC identity, and uploads them
  with [trusted publishing](https://docs.pypi.org/trusted-publishers/): no
  API token, the job's identity under the `pypi` environment is what PyPI
  trusts, and what the attestations prove.

## Coding guidelines (non-negotiable)

1. **Strict, strongly-typed Python.** Pyright runs in `strict` mode and must be
   clean. Never use `Any`, `cast`, or `# type: ignore` in `src/`. Narrow with
   `isinstance` and `TypeGuard` instead. Every function is annotated (ruff's
   `ANN` rules enforce it). Protocol types from the socket are untrusted: parse
   them through guards that name the offending field, never trust a shape.
2. **The gate must always pass.** `./zuke ci` runs format check, lint,
   type-check and tests, the same gate CI runs; it must be green before a
   commit.
3. **Keep test coverage at 95%+ (lines and branches) at all times.** Enforced
   by pytest's `--cov-fail-under`. New code needs new tests in the same change.
4. **Document every public symbol.** A docstring on every public module, class,
   function and attribute. Match the density and tone of the existing ones.
5. **Tests are hermetic and fast.** No network, no reliance on ambient tools.
   A test that needs a subprocess runs `sys.executable`, which is always
   present. A test that needs the engine uses a fake engine speaking the
   protocol over a loopback socket, never a real one; the conformance suite
   from the engine repository is the contract.
6. **Public API is task-shaped.** Operations live on the `*Tasks` facades the
   generator emits and on `ctx`, never as loose module-level helpers. Keep
   internal helpers unexported (`_name`).
7. **One domain per file.** The DSL, the manifest, the worker loop, the
   context, the bootstrap and the facades are separate modules under
   `src/zuke/`. A single file accreting everything is a smell.
8. **Every source file starts with the copyright and license header.** All
   `.py` files, tests and fixtures included, open with:

   ```python
   # Copyright (c) 2026 the Zuke contributors
   # SPDX-License-Identifier: MIT
   ```

   `tests/test_license_headers.py` fails the suite on any file missing it.

9. **No dead code.** Remove unreachable branches, unused helpers and fallbacks
   whose condition can never fire. Tighten the type instead of guarding a loose
   one.
10. **Reuse the helper; never paste a second copy.** A near-copy differing by a
    constant or a message is a copy-paste: parameterise it. A guard or an
    escape whose whole value is being applied everywhere has exactly one
    implementation.
11. **Configuration is a fluent settings lambda, not an options object**, as in
    the TypeScript SDK: `target().retry(3).timeout("5m")`, `Docker.build(lambda
    s: s.tag("app:1"))`. Each setter returns `self`.
12. **Mirror the engine's vocabulary.** The manifest fields, the RPC method
    names and the `ctx` surface are named exactly as the engine's protocol
    names them, so the two repositories can be read side by side.

## Testing

Every change ships tests in the same PR. Two layers:

1. **Unit, `tests/test_*.py`.** One module in isolation, with fakes. The bulk
   of the coverage.
2. **Protocol, `tests/protocol/`.** The SDK's worker, started as the process
   the engine would start, against a fake engine over a real loopback socket,
   replaying every conformance case vendored under `tests/protocol/cases/` from
   the engine release `VERSION` names: the case's calls in order, its scripted
   answers, a worker that crashes mid-body, and an engine that dies. The
   build's `vendor_cases` target refreshes the cases from an engine checkout
   at a tag and records the tag in `VERSION`.

Name every test module `test_*.py`; pytest discovers nothing else.

## Commands

| Task                        | Command                                                    |
| --------------------------- | ---------------------------------------------------------- |
| Install the environment     | `uv sync`                                                  |
| List the targets            | `./zuke --list`                                            |
| Run tests with coverage     | `./zuke test`                                              |
| Type-check                  | `./zuke check`                                             |
| Format / check formatting   | `./zuke fmt` / `./zuke fmt_check`                          |
| Lint                        | `./zuke lint`                                              |
| Pre-commit gate, same as CI | `./zuke ci`                                                |
| AI review of the diff       | `./zuke review` (skipped without `OPENAI_API_KEY`)          |
| Regenerate the CI workflow  | `./zuke generate-ci` (`--check` verifies it is current)    |
| Vendor the conformance cases | `./zuke vendor_cases --engine-repo <checkout> --engine-tag <tag>` |
| Vendor the tool spec        | `./zuke vendor_spec --engine-repo <checkout> --engine-tag <tag>` |
| Regenerate the facades      | `./zuke facades` (`facades_check` verifies they are current) |
| Regenerate `uv.lock`        | `uv lock`                                                  |
| Regenerate `deno.lock`      | `./zuke lock` (`vendor_spec` relocks; `lock_check` is in the gate) |
| Publish a cut release       | `./zuke publish` (the `release` workflow runs it on `main`) |
| Sync with the engine        | `./zuke sync_engine` (the daily `sync` workflow runs it; the pull request needs the App credentials) |
| Generate the API reference  | `./zuke api_reference` (writes `.zuke/api.json`)          |
| Sync it to the website      | `./zuke sync_website` (the `release` workflow runs it after `publish`; skipped without the App credentials or `WEBSITE_SYNC_TOKEN`) |

`./zuke` (`./zuke.ps1` on Windows) runs `@zuke/engine` at the version
`zuke.json` pins, which starts `build.py` as its worker; every command a target
runs goes through the engine. The lock is part of the gate: CI runs
`uv sync --locked`, so a change to `pyproject.toml` must come with a
regenerated `uv.lock` in the same commit. The engine side is locked too:
`deno.lock` pins the engine, every wrapper release `spec/engine.json` names and
the `@zuke/core` they resolve, and the launchers run frozen against it, so a
release missing from the lock fails the run. `./zuke lock` rewrites it (and
`vendor_spec` does so itself); after bumping `zuke.json`'s engine, delete
`deno.lock` first, since the frozen launcher cannot start an engine the lock
does not name, then run `./zuke lock`. `lock_check` fails the gate when the lock
is absent, misses a release, or differs from the commit. `.github/workflows/ci.yml` is
generated from `build.py`'s `ci_workflow` field: edit the field, run
`./zuke generate-ci`, and commit both; `.github/workflows/ai-review.yml` is
generated the same way from its `ai_review` field,
`.github/workflows/release.yml` from its `release_workflow` field, and
`.github/workflows/sync.yml` from its `sync_workflow` field.

**Following the engine.** `sync_engine` runs daily and on demand. It finds the
engine repository's newest `cli-v*` tag, the commit the `zuke` binary of that
release is compiled from, and does nothing when `spec/engine.json` and the
cases' `VERSION` already name it. Otherwise it vendors that tag's cases, tool
spec and wrapper versions, pins `zuke.json` to the engine release of that
commit, relocks and regenerates the facades, and, with the `zuke-build` App's
credentials, force-pushes the result to the one `sync/engine` branch: it
opens an issue and a pull request closing it, or retitles the open one. The
title is `feat:` when the facades changed and `fix:` otherwise. That tag, not
a newer engine tag, because the binary embeds exactly its releases: a facade
must never ask the binary for a wrapper release it lacks. A red gate on the
sync pull request is the SDK work the release needs.

## Repository layout

```
build.py                  # this repository's Zuke build: the gate, the vendoring, the facades, the CI workflow
zuke.json                 # names the worker command and the @zuke/engine version the launchers run
zuke, zuke.ps1            # the bootstrap launchers, copied from the engine repository
pyproject.toml            # package metadata, the dev tools, tool config
uv.lock                   # the locked development environment
deno.lock                 # the engine, the wrappers and @zuke/core, frozen; ./zuke lock rewrites it
src/zuke/                 # the package (src layout): the peer, the worker loop, the authoring surface, the contexts
src/zuke/tools/           # the generated facades, one module per engine wrapper; never edited by hand
spec/                     # the engine's tool spec and the wrappers' versions, vendored at a tag
tests/                    # pytest suite; protocol/ replays the engine's conformance cases, vendored under cases/
.github/workflows/ci.yml  # the gate on ubuntu, macOS and Windows, generated from build.py
.github/workflows/ai-review.yml  # the AI review on pull requests and on command, generated from build.py
.github/workflows/release.yml    # release-please and the PyPI publish on main, generated from build.py
.github/workflows/sync.yml       # the daily engine sync's pull request, generated from build.py
.release-please-config.json, .release-please-manifest.json  # the release configuration and the last released version
.github/ISSUE_TEMPLATE/   # feature, bug and chore templates; blank issues are off
AGENTS.md                 # this file; CLAUDE.md points here
```

## Good open-source practices to follow

- **Every change starts with an issue.** Feature, bugfix, documentation,
  refactor or chore: file it from the templates first, then open the pull
  request that closes it with `Closes #<n>`. This applies to agent-authored
  work exactly as to a human's.
- **PR titles are the release trigger.** The repository squash-merges, and
  release-please parses only the squashed subject. Title every PR as a
  Conventional Commit: `feat: …` for a minor bump, `fix: …` for a patch;
  `docs`, `chore`, `refactor` and `test` never bump.
- **Keep code snippets out of commit message bodies.** A fragment with
  parentheses can make release-please drop the commit from the release.
- **Pin GitHub Actions by commit SHA** with the version in a trailing comment,
  so Dependabot can bump them. Never a floating tag.
- **Always read the reviewer comments on every PR.** The AI reviewers of the
  engine repository run here too, through `zuke.tools.ai` in `build.py`'s
  `review` target: a security review and a code-quality review post one
  comment per run, each finding under a short id. Address or answer each
  finding, quoting its id; a maintainer's reply quoting an id is weighed as a
  rebuttal on the next run, which `@zuke-build review` starts without a push,
  and `@zuke-build accept <id> <reason>` records a finding as intended.
- **No secrets or machine-specific paths** in the repository or commits.
- **Update docs with code.** If behaviour changes, update `README.md` and the
  docstrings in the same PR. The docstrings are the API reference the website
  renders at zuke.build/api/python: `_reference.py` reads them with `ast` into
  the same `api.json` contract the engine repository emits for TypeScript, and
  the `release` workflow's `sync_website` step opens and auto-merges a website
  PR with it on every release. It pushes with a `zuke-build` App token it
  mints from `ZUKE_BUILD_APP_ID` and `ZUKE_BUILD_APP_KEY`, scoped to the
  website with contents and pull-requests write; `WEBSITE_SYNC_TOKEN`, when
  set, is used instead.
